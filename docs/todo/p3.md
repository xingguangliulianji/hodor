# P3 — 阶段 13–14：VPS Docker 自托管

全量待办与完成状态维护在 [TODO 总表](/todo/index.md)。本页是主线阶段 1–7 逐渐完善后的自托管方向：同一代码库同时支持 Cloudflare Workers 与 VPS Docker 两种部署，Cloudflare 路径保留不动。当前仅立项，启动时间另定。

::: info 可行性评估结论（2026-09-30，启动时直接复用）
现状是 Cloudflare Workers（workerd 运行时）+ D1，不是 Node 服务，直接加 Dockerfile 不可行。有利条件：零运行时依赖、纯 Web 标准 API、D1 用法面窄（仅 `prepare → bind → first/run`，RETURNING 为 SQLite 原生能力）、无 `waitUntil` 依赖且路由为纯函数。既定路线：可移植核心改造 + Node 24 第二入口（内置 `node:sqlite`，零新增运行时依赖），而非容器包装 `wrangler dev` 的开发模拟器方案。约束：webhook 模式需要公网 HTTPS（反代 / 隧道）；长轮询（getUpdates）模式免域名免 TLS，是 VPS 自托管的首选形态。
:::

## 阶段 13 — 双运行时可移植核心 {#stage-13}

**交付**：共享层（routes / pipeline / store / telegram）与 Workers 运行时解耦，类型收窄为可移植形态；行为零变化，Cloudflare 部署路径不受影响。

**不做**：不实现任何 Node 运行时代码、不新增依赖、不改 Cloudflare 部署与数据库。

**依赖**：阶段 2–3 已验收；推荐阶段 7 稳定基线后启动。

- **T59** 可移植类型 HodorEnv / HodorDB —— 验证：共享层不再直接引用 `Cloudflare.Env` / 全局 `D1Database`（按实际用量结构兼容收窄），typecheck 与全部现有测试绿，Workers 行为不变。
- **T60** 共享路由 route() 抽取 —— 验证：Workers 入口与未来 Node 入口共用同一分发逻辑；/health、管理端点、/webhook 回归行为不变。

**验收**：typecheck 与现有 vitest 全绿，`npm run deploy` 部署后功能回归无差异；共享层对 Workers 运行时零硬编码依赖。

## 阶段 14 — VPS Docker 自托管 {#stage-14}

**交付**：Node 24 + node:sqlite 第二运行时与容器交付，含长轮询模式；裸 VPS 无域名无 TLS 即可运行。

**不做**：不替代 Cloudflare 部署路径；不做多实例 / 集群与分布式幂等；webhook 模式不自带 TLS（交给反代 / 隧道）。

**依赖**：阶段 13。

- **T61** node:sqlite D1 形状适配器 + 迁移 runner —— 验证：prepare/bind/first/run 与 RETURNING 语义对齐 D1，PRAGMA user_version 跟踪迁移，重复启动不重复执行，单测覆盖往返与建表。
- **T62** Node HTTP 入口与 process.env 装配 —— 验证：HODOR_DB_PATH / RUN_MODE（webhook|polling）/ PORT 运行时变量生效，必填缺失 fail-fast 且可诊断，/health 返回 200。
- **T63** getUpdates 长轮询模式 —— 验证：与 webhook 互斥，启动先 deleteWebhook，复用 processed_updates 幂等状态机；裸 VPS 无域名双向收发，重推 / 幂等 / 毒丸行为与 webhook 一致，日志不泄漏 token。
- **T64** Docker 交付 —— 验证：多阶段 Dockerfile（node:24-slim）、非 root 运行、VOLUME /data 持久化、HEALTHCHECK /health，compose + env 示例开箱可用；容器重建数据不丢。
- **T65** 部署文档 —— 验证：docs/guide/deploy-docker.md + README 双部署入口；从零 VPS 按文档跑通轮询与 webhook 两种模式。

**验收**：docker compose up 后，轮询模式在裸 VPS（无域名）完成双向聊天冒烟；SQLite 数据落挂载卷，容器重建不丢；Cloudflare 路径部署与功能不受影响。
