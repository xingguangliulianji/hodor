# P1 — 阶段 1–7：单 bot 主线

全量待办与完成状态统一维护在 [TODO 总表](/todo/index.md)。本页按阶段引用 T 编号，明确最小交付范围与验收；先完成阶段 1 + 2，再逐轮叠加能力。

::: tip MVP 边界
阶段 2 完成后仅供受信任小范围自用，不含人机验证与管理命令全集，不作为公开运行版本。Webhook 鉴权、指定群组校验、管理员校验、持久化映射与基础失败处理不能省略。
:::

## 共通约定

- 沿用[六张表 schema](/guide/database.md)及 `bot_id` 预留，按阶段启用业务能力，不为缩小 MVP 推倒数据模型。
- 每项功能的自动化测试与必要文档随实现完成，不等阶段 7 补齐；每轮回归此前已验收链路。
- 每个可运行增量部署后，在浏览器 / Telegram / D1 Console 验收；过期、并发及 API 异常用自动化测试验证。
- 本页编号用于编排，不重复维护勾选状态；总表只有在核验实现和验收证据后才能勾选。

## 阶段 1 — 部署地基 {#stage-1}

**交付**：可部署 Worker、可读写 D1、六表迁移与测试基座；一条命令 `npm run deploy`（自动解析/创建 D1 → 远端迁移 → 部署）；版本注入与 release-please / CI（2026-09-30 提前纳入，见[总表变更记录](/todo/index.md#变更记录)）。

**不做**：完整健康诊断（T07）、fork 全流程回归与 README/文档同步（T12）、运维 SQL（T10）。

**依赖**：无。

- **T01** 工程与基础 `/health` —— 验证：部署后端点返回 `{"status":"ok","version":<package.json 版本>}`。
- **T02** D1 绑定与 `keep_vars`（建库已由 T05 自动化取代）—— 验证：Worker 可读写数据库，重复部署不覆盖 dashboard 变量。
- **T03** 六表迁移 —— 验证：D1 Console 查到六张表，重复执行迁移不丢已有数据。
- **T04** 测试基座与冒烟用例 —— 验证：测试可访问迁移后的数据库且全部通过。
- **T05（核心）** 部署脚本自动建库绑定 —— 验证：首次 `npm run deploy` 自动创建 D1 并绑定 `HODOR_DB`；重复部署复用原库；仓库 `database_id` 保持占位符；权限不足输出 API token 引导且不泄漏 token。
- **T06（核心）** 部署自动迁移 —— 验证：新部署自动建表；重复部署迁移 no-op；迁移失败中止发布、不部署不兼容代码。
- **T08** 版本注入 —— 验证：`/health` 版本与 package.json 一致；版本模块 gitignored，干净检出上测试可跑。
- **T09（核心）** Release Please + CI —— 验证：push 后 CI 绿、release-please 开出 Release PR（限定官方仓库运行）；合并发版的完整链路（tag → GitHub Release → `/health` 版本更新）随阶段 2 MVP 首次走通。

**验收**：`npm run deploy` 一条命令走通建库、迁移、部署，`/health` 返回 ok 与版本号；push 后 CI 与 Release PR 出现；六表齐备且迁移幂等。此时尚不宣称 bot 可聊天。

::: info 部署方式（2026-09-30 起）
部署自动化自本阶段起可用：本地走 `npm run deploy`；Cloudflare Workers Builds 使用**官方默认命令**（部署 `npx wrangler deploy`、预览 `npx wrangler preview`）零改动可用——自动建库与迁移挂在 install 步骤的 postinstall 钩子上，按 `WORKERS_CI=1` 门控，本地与 GitHub Actions 环境安全跳过。fork 用户视角的「全浏览器、零命令」部署体验仍以阶段 7 验收为准，公开[部署流程](/guide/deploy.md)在阶段 7 前不视为已兑现承诺。
:::

## 阶段 2 — 最小 MVP：文本双向聊天 {#stage-2}

**交付**：单 bot / 单群组；用户发文本自动建档并创建 topic，管理员直接在 topic 回复可送达。

**不做**：媒体完整验收、欢迎语与置顶、完整消息账本、验证码、管理命令与完整自检。

**依赖**：阶段 1。

- **T13** Webhook 绑定、secret_token 注册、`getMe` 写入身份与回显 —— 验证：绑定指向本 Worker；缺失或错误管理密钥统一返回 401 +「无效的管理密钥」，日志不泄漏密钥。
- **T14** Webhook 解绑 —— 验证：正确鉴权后 `getWebhookInfo` 显示未绑定，错误密钥不能操作。
- **T15** Webhook 鉴权与来源分流 —— 验证：伪造 secret 返回 401；其他群组、不支持的 update 安全忽略，不触发转发。
- **T19** 首条文本建档 —— 验证：不输入 `/start` 也能开始聊天，用户记录正确。
- **T20** topic 创建、命名与持久化双向映射 —— 验证：再次联系和重新部署后复用原 topic；并发首次联系不产生多个有效绑定或遗留重复 topic。
- **T21** 文本双向中继与管理员校验 —— 验证：两个用户不串线；管理员直接发言送达，非管理员发言静默忽略。（运行时说明：生产实测当前 bot 的 `copyMessage` 全场景 400「message to copy not found」，系 Telegram 侧账号级异常。最终定稿**双向均用 `sendMessage`**——topic 内干净渲染，身份由 topic 标题 + 客户端话题标签承载，T24 置顶信息补足；`forwardMessage` 保留为 T22 媒体「带身份」备选，T22 干净媒体走 per-type send）
- **T16** 幂等与并发控制 —— 验证：已完成 update 重放不重复转发；处理失败不被当成成功跳过；并发重复投递有测试覆盖。
- **T17** 失败重推与防毒丸 —— 验证：暂时失败可重推恢复；达到 `MAX_ATTEMPTS` 后标记失败并跳过，不无限阻塞，失败可定位。

**验收**：两个真实用户各建独立 topic，文本往返正确；非管理员、其他群组及重复投递不能绕过上述约束。

::: warning 幂等边界
`processed_updates` 不等于端到端严格“一次送达”。Telegram 已发送成功但数据库写入失败时，重推仍可能重复发送。本阶段须用测试与说明明确部分成功窗口的策略和风险，不得提前标记 processed 来掩盖失败、造成消息丢失。
:::

## 阶段 3 — 聊天体验完善 {#stage-3}

**交付**：常用媒体、欢迎语、用户信息置顶与可查询双向消息账本。

**不做**：验证码、封禁、备注、高危标记与会话清理。

**依赖**：阶段 2。

- **T22** 常用媒体直传 —— 验证：图片、视频、语音、文件、贴纸、动图逐类双向实测；不可复制消息受控处理，不无限重试，不宣称任意类型均可复制。
- **T23** 欢迎语与 `/start` 频控 —— 验证：首次联系有欢迎语；每用户每分钟最多响应一次，反复 start 不刷回复、不新建 topic。
- **T24** 用户信息置顶 —— 验证：昵称、ID、首次聊天时间正确，置顶不重复；验证尚未启用时不伪称已验证。
- **T25** 双向 messages 账本 —— 验证：文本与媒体的方向、群内 / 私聊 ID、类型可查询；管理员消息 ID 完整，供后续清理使用。
- **T26** 无绑定 topic 提示 —— 验证：只在指定群组向管理员提示，不误发其他用户、不产生未捕获异常。

**验收**：常用消息双向可用，用户身份可识别，D1 消息记录完整；阶段 2 文本闭环继续通过。

## 阶段 4 — 安全试运行 {#stage-4}

**交付**：默认数学题验证、分钟限频、提示频控、帮助与封禁、429 有界重试。

**不做**：验证开关、纯按钮模式、TTL 到期重验、备注及危险清理。

**依赖**：阶段 3。

- **T34** 命令分流与 `/help` —— 验证：仅指定群组 topic 中的管理员可执行；帮助只展示已交付命令，未知命令不误发用户。
- **T27** 数学题验证 —— 验证：四个答案按钮、答错重出、答对放行并更新置顶；其他用户或旧题回调不能代答。
- **T28** 未验证拦截 —— 验证：首次和存量未验证用户均先验证；答题前消息不创建客服 topic、不转发、不积压补发，通过后只转发新消息。
- **T29** 固定窗口限频与超限重验 —— 验证：上限设为 3 时第 4 条被拦截，提示含数字；跨窗口计数恢复，超限不等同封禁。
- **T30** 提示类回复频控 —— 验证：持续刷消息不会持续触发欢迎语、验证码、禁言或超限回复；错误答题与旧回调不能绕过频控。
- **T35** `/ban` / `/unban` —— 验证：封禁后消息不转发，禁言提示限频；解禁恢复正常验证与限频流程。
- **T18** 429 有界重试 —— 验证：按 retry_after 重试一次；持续限流或等待超出执行预算时受控失败，不无限等待。

**验收**：真实账号走通答题、答错、超限与封禁；自动化覆盖回调归属、提示频控及 429。通过后可受控扩大试用，但验证码不保证阻止所有滥用，也不消除进入 Worker 的请求成本。

## 阶段 5 — 日常管理 {#stage-5}

**交付**：备注、高危标记、验证开关、纯按钮模式与验证有效期。

**不做**：删除用户、清空 topic 消息与全局清库。

**依赖**：阶段 4。

- **T36** `/note` / `/unnote` —— 验证：备注增删即时更新置顶、存于 topic；阶段 6 重开流程继续保留备注。
- **T37** `/risk` / `/unrisk` —— 验证：置顶标注正确，24 小时内不重复高危提示，正常聊天不受影响。
- **T31** settings 与 `/verifyon` / `/verifyoff` —— 验证：开关即时生效且重部署不丢失；保留验证记录，重新开启后按记录及有效期判断是否重验。
- **T32** `/verifymode` 与动态帮助 —— 验证：新题使用所选模式，旧题回调不能误通过；帮助随开关变化，并说明纯按钮防护较弱。
- **T33** 验证有效期 —— 验证：自动化覆盖 `VERIFY_TTL_HOURS=0`、过期边界、重验及开关组合，无需人工等待。

**验收**：日常操作与置顶状态一致，验证设置持久有效，阶段 4 拦截规则不退化。

## 阶段 6 — 会话维护与危险操作 {#stage-6}

**交付**：原生 topic 状态同步 → `/archive` 软归档 → `/deluser` 物理删除 → `/purgemsg` → `/wipealldata`，各项独立验收。

**不做**：Hodor `/close` 命令、删除双方私聊窗口历史、跨实例迁移。

**依赖**：阶段 5；所有危险操作再次校验管理员与目标 topic/user 范围；Telegram 服务消息只同步 topic 状态，不触发用户归档或数据删除。

- **原生状态同步**：客服群 `forum_topic_closed` / `forum_topic_reopened` 只更新 topics.status/closed_at；服务消息零中继、零账本。官方定义 closed topic 不能收消息，Hodor 不依赖关闭后发送确认。
- **T38 `/archive` + `/deluser`**：archive 清验证、软删除标记、关 topic，保留 users/topics/messages/note；回访自动重开并重新验证，topic-gone 时重建替代 topic。deluser 二次确认后删除 Telegram topic 与其中群内消息并清对应 users/topics/messages；不删除私聊历史；topic 已不存在按已删处理，其他永久删除失败保留 D1 行。
- **T39 `/purgemsg`**：仅按账本删除当前 topic 可追踪群内消息（含管理员发言）+ 置顶并重置；部分失败明确报告，不把未删除内容标为已清空；不删除私聊消息或 topic。
- **T40 `/wipealldata`**：警告说明将删除/保留范围；确认回调再次鉴权、60 秒有效期；取消、超时、伪造/重放不清库；确认后**先删除客服群内全部话题（General 除外）及其中消息**，全部成功后清 users/topics/messages/delete_confirmations、保留 settings/processed_updates/bots；有话题删除失败则不清库并报数，重新发起可续删。

**验收**：隔离测试覆盖原生 close/reopen 事件、archive 回访/重验、deluser 二次确认和部分失败、局部清理、全库确认；真机确认 Bot API 实际权限/反馈后再开放日常使用。

## 阶段 7 — 公开发布体验 {#stage-7}

**交付**：完整 v1 与面向 fork 用户的部署、更新、诊断体验。

**不做**：多 bot、换绑迁移与 TGuard。

**依赖**：阶段 6；前序功能测试与必要文档应已完成，本轮做发布集成回归。

- **T05（核心已于阶段 1 交付）** 本阶段验收 fork 场景 —— 验证：fork 后首次构建创建品牌前缀 D1 并绑定 `HODOR_DB`；重复部署复用原库；权限不足时 API token 引导可用且不泄漏 token。
- **T06（核心已于阶段 1 交付）** 本阶段验收升级恢复 —— 验证：已有数据实例升级成功；迁移失败不继续发布不兼容代码，数据保留，可重跑恢复。
- **T07** 完整自检 `GET /selfcheck`（`/health` 保持纯存活探针）—— 验证：环境变量（含三密钥互异与选填值域）、七表、Webhook 指向均可检查；缺配置、缺表、未绑定或错误绑定可定位，不回显密钥。
- **T08（已于阶段 1 交付）** 随发布回归 —— 验证：各次发版后 `/health` 版本与 package.json 一致。
- **T09（核心已于阶段 1 交付）** 首个 Release 完整链路 —— 验证：官方仓库自动生成 Release PR、tag、GitHub Release；部署版本更新，fork 默认手动 Sync fork 跟随。
- **T10** 运维 SQL —— 验证：D1 Console 逐条执行，能查询用户、topic、消息与失败 update。
- **T11** 发布回归 —— 验证：入站、出站、验证、限频、命令、幂等与端点鉴权全部通过，部署自动化不破坏配置和数据。
- **T12** README / 文档与从零验收 —— 验证：新实例按 fork → 连接 → 配置 → 部署 → 绑定 → 验证 → 聊天走通；已有实例 Sync fork 更新后版本、配置与数据正确。

**验收**：全新实例完成公开部署流程，已有数据实例完成升级；阶段 1–7 全部通过后再发布完整 v1。
